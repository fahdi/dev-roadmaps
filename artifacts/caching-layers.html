Caching, Layer by Layer

A cache is not a speed setting. It is a copy of the truth that is allowed to be wrong for a while, and every hard caching problem is really a question about that window. Pick a stampede below and see which fix actually applies.

~0 ms

Client

On device

Nearest and cheapest. You cannot invalidate it, so anything you put here you are choosing to live with until it expires.

~10 ms

Edge / CDN

Near the user

Shared across users in a region. Great for the same bytes for everyone, useless for per-user data.

~1 ms

Server cache

Redis, in memory

One hop from your service and shared by every instance. This is the layer that absorbs read load, and the one that stampedes.

~200 ms

Origin

The database

The only layer that is definitely correct, and the one you are trying not to call. Everything above exists to protect it.

Which stampede?
Protection
Origin queries1000 in the burst

The stampede is not caused by the cache being slow. It is caused by everyone missing at the same instant.
Which is why the fix depends on why they are synchronised. One key everyone wants needs a lock. A thousand keys written together need their expiry spread out.
Apply the wrong one and the graph does not move.
Roadmap: know which layer you are on, know what it costs to be wrong there, and know which stampede you are preventing.
