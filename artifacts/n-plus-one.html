The N+1 Query

Render a list of posts, show each author's name. The lazy version issues one query for the list and then one more per row. It is the most common performance bug there is, and the reason is that on your laptop it is genuinely fine.

Lazyone query per row
Batchedone IN (...) for authors
Eager joinone query, joined

Lazy

N + 1 queries

Fetch the posts, then touch post.author in the template and the ORM quietly issues another query. Per row.

Nothing in the code looks wrong. That is the whole problem: the loop is in the view, and the cost is in the driver.

Batched

2 queries

Collect the author ids from the rows you already have, then fetch them all in one WHERE id IN (...) and stitch them together in memory.

This is what a dataloader does. Constant query count regardless of row count, which is the property that matters.

Eager join

1 query

Ask the database to do the join. Fewest round trips, and the planner gets to see the whole intent at once.

Watch for duplicated parent rows on one-to-many joins, where batching is often the better shape despite the extra query.

N+1 is not a slow query. Every one of those queries is fast.
It is a round-trip problem, so it scales with your list length and your network distance, neither of which is realistic on a laptop.
Count queries per request in development. It is the only version of this bug you can see before a customer does.
Roadmap: measure query count, not just query time. One is visible locally, the other only in production.
Pairs with Latency, Throughput, Bandwidth, Jitter for why round trips dominate, and Caching, Layer by Layer for what to do once the count is already low.
