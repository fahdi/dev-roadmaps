12 Prompt Patterns

"Write a better prompt" is not advice. These are the actual moves, grouped by what each one changes: how much you show, how you steer the reasoning, how you constrain the output, and what the whole thing costs.

How much you show

Examples are the cheapest way to communicate a format

01Zero-Shot

No examples, just the ask. Fine when the task is common and the output shape is obvious.

When is zero-shot enough?
02One-Shot

A single example sets the shape. Often the largest jump in reliability you will get for the fewest tokens.

Why does one example help so much?
03Few-Shot

A handful of examples to copy from. Returns flatten quickly, so more is not automatically better.

How you steer the reasoning

Change how the model gets to the answer, not just what you ask for

04Chain of Thought

Make it show the steps, reasoning first and answer last. Costs tokens and latency, so it is not free.

When does chain of thought hurt?
05Role Prompting

Give it a job title. The role mostly picks the vocabulary and level of detail rather than adding knowledge.

06Self-Reflection

Draft, critique, revise. A second pass catches format and consistency errors the first pass missed.

How you constrain the output

The difference between a demo and something a program can consume

07Structured Output

Ask for something parseable rather than prose, and validate it rather than trusting it.

08Delimited Sections

Wrap each section in explicit tags so the model can see where instructions end and data begins.

09Constraints

State length, tone and what to leave out. Most rambling is an unstated limit, not a model failure.

What it costs

Prompts are code that runs on every request, and gets billed on every request

10Context Selection

Pick what actually enters the window: gather candidates, rank them, admit only the top few.

11Templates

One prompt, many inputs, under version control. The same prompt everywhere means one place to fix.

12Prefix Caching

Keep the stable prefix byte-identical so it can be reused across calls. A single stray character invalidates it.

Patterns compose. Pick the smallest set that works.
Most production prompts are two or three of these, not twelve.
Stacking every pattern at once makes the prompt expensive, slow, and impossible to attribute when quality moves.
Some tasks no prompt pattern will fix.
A model reads text as tokens, which are chunks of characters rather than the characters themselves. Inside a token the individual letters are not separately visible, so counting letters, spelling a word backwards or manipulating text character by character is unreliable no matter how you phrase the request.
That is a property of the input representation, not a prompting failure. Hand those jobs to code and let the model orchestrate the call.
Roadmap: start with the fewest examples that work, steer the reasoning only when the task needs it, constrain the output so code can consume it, then make the whole thing cheap to run.
Pairs with Context Engineering for what belongs in the window, and LLMOps for versioning and evaluating prompts once they ship.
