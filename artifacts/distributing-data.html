Distributing Data Across Nodes

What actually happens when one machine stops being enough. Consistent hashing and CAP get name-dropped constantly and explained rarely, so here they are in the order the problem forces on you.

1

The problem: one machine runs out

Traffic, storage or both outgrow a single node, so data has to be split across several. The instant you do that, you need a rule for which node owns which key, and every node needs to agree on that rule.

2

The naive answer, and why it breaks

Hash the key and take it modulo the node count. It distributes evenly and it is one line of code. It also fails the moment the node count changes, because the divisor is part of the formula.

Go from four nodes to five and almost every key maps somewhere new. That is a near-total reshuffle triggered by adding one machine, which is exactly when your system is already under stress.

3

Consistent hashing: arrange it on a ring

Hash both keys and nodes onto the same circular space. A key belongs to the first node it meets going clockwise, which means each node owns only the arc behind it.

Now adding a node splits one arc instead of rewriting the map. Only the keys in that slice move, and the rest never notice. Removing a node hands its arc to the next one along, and the blast radius is again a single slice.

4

Virtual nodes: fixing the lumpy ring

With a handful of nodes, random placement leaves wildly uneven arcs, so one machine gets far more than its share. The fix is to give each physical node many positions on the ring rather than one.

More positions means the arcs average out and load evens up. It also spreads the recovery work: when a node dies, its many small slices are absorbed by many different neighbours instead of dumping everything onto one.

5

Replication: more than one copy

Owning a slice is not enough, because a node loss would take its data with it. Each key is stored on the next several nodes around the ring, so a copy always survives.

This is where read and write quorums come in. If you require enough overlap between the nodes you write to and the nodes you read from, a read is guaranteed to see the latest write. Loosen that and reads get faster but may return stale data.

6

CAP: what you give up when the network splits

Consistency, availability and partition tolerance. The framing says pick two, but that undersells it: networks fail whether you plan for it or not, so partition tolerance is not optional in a distributed system.

CP Refuse the request rather than risk a wrong answer. Choose this when correctness matters more than uptime.
AP Answer anyway and reconcile afterwards. Choose this when being down is worse than being briefly stale.
CA Only coherent on a single node. A classic relational database on one machine, which is a real and often correct choice.

Treat these as tendencies rather than labels. Most modern databases let you tune the quorum per query, so the same system can behave closer to CP for a payment and closer to AP for a page view.

The real question is what happens during a partition.
Consistent hashing decides where data lives and keeps rebalancing cheap. Replication decides how many copies survive.
CAP is not a menu you pick from once. It is the behaviour you have already chosen, whether deliberately or by accepting a default.
Roadmap: split the data, place it on a ring, even it out with virtual nodes, replicate for survival, then decide what a partition does to you.
