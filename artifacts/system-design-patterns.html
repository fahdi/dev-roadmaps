12 System Design Patterns

The patterns that keep a distributed system standing when one of its dependencies misbehaves. Ordered easy to hard, because the later ones assume you already have the earlier ones.

Easy to hard · learn them in this order

Fail fast, then recover

What to do when a dependency is slow or down

01Timeout

Fail fast, do not hang.

A hung call still holds a thread. Cut it at a budget you chose rather than whatever the default is.

What timeout would you actually set?
02Retry

Try again, but politely.

Back off exponentially and add jitter, or every client retries in lockstep and rebuilds the spike you were recovering from. That fixes the herd but not the side effects: a retried write needs an idempotency key so the second attempt is recognised as the same request rather than performed again.

Is this operation safe to repeat?
03Circuit Breaker

Closed, open, half-open.

After repeated failures, stop calling entirely. A probe decides when to reopen, not a timer alone.

What reopens the circuit?

Shed load and contain it

Stopping one problem from becoming every problem

04Rate Limiter

Shed load before it hurts.

Refuse the excess request cheaply and early. Shedding some traffic beats collapsing under all of it.

Token bucket or fixed window?
05Bulkhead

One leak, one compartment.

Give each dependency its own pool. When one is drowning, the others keep serving.

Why isolate thread pools?
06Pub / Sub

One event, many listeners.

The publisher never waits on consumers, so adding a consumer costs the producer nothing.

At-least-once or exactly-once?

Where the data lives

Caching and storage choices, and what each one trades

07Cache Aside

Miss, fetch, then store.

The application owns the cache, not the database. Simple, and invalidation becomes your problem. Watch the moment a hot key expires: every concurrent miss goes to the database at once, so one expiry becomes a traffic spike. Let a single request do the fetch and have the rest wait on it.

What happens the instant a hot key expires?
08Write-Through

Write both, never stale.

No acknowledgement until the database has it. Slower writes bought in exchange for never serving a stale read.

What does that cost you?
09Event Sourcing

The log is the truth.

Append events instead of overwriting state. Current state is a replay, so history is never lost.

How do you replay state?

Evolving the system

The hard ones, for when the architecture itself has to change

10CQRS

One writer, many readers.

Split reads from writes so each scales separately. The read side lags deliberately, which you have to design for.

How much read lag is acceptable?
11Saga

No rollback, only undo.

There is no distributed transaction to roll back, so each completed step needs a compensating action.

How do you undo step two?
12Strangler Fig

Replace it route by route.

Move traffic across one path at a time. The old system dies last, and never in a single cutover.

When do you finally kill the legacy?
Every one of these is about failure, not throughput.
Timeouts, breakers and bulkheads decide what happens on your worst day rather than your average one.
Systems rarely fall over because a dependency broke. They fall over because nothing was in place to stop that break spreading.
Roadmap: bound every call, retry politely, break the circuit, shed and isolate, then choose your data and evolution patterns deliberately.
