When the Service is a Model

The first half of the journey is unchanged — DNS, TLS, CDN, balancer, gateway all still happen. What changes is everything behind the gateway: the reply is generated token by token rather than fetched, so the work splits into four phases.

Request Edge routing to the nearest point of presence Authentication before anything runs Rate limits so no one caller floods the system
Context Conversation state loaded from the history store Context assembly packs prompt plus evidence Policy checks screen against safety rules
Infer Model routing picks the right model for the job GPU scheduling batches the work efficiently Hot cache serves session and prompt reuse
Stream Token streaming as the answer generates Billing & metering counts tokens in real time Logging & evals record and score every call

Two things have no equivalent in the plain web request: the reply starts arriving before it is finished, and the call has to be retry-safe — a dropped connection must not bill the user twice. Storage and observability keep running after the last token ships.

Journey: DNS → TCP/TLS → CDN → Load Balancer → API Gateway → Service → Cache → Database → back. Real architectures vary — the gateway and balancer are often combined, and either can come first — but this is the shape to reason from.
